# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

NestJS 12 + Apollo GraphQL (code-first) + Prisma/PostgreSQL e-commerce backend, Ghana-first (GHS, Paystack, MoMo, COD).

## Working state (read first)

Work follows a phased roadmap. **[`docs/roadmap/STATUS.md`](docs/roadmap/STATUS.md) is the live state of the work.** It holds the current phase, the active task and its exact next step, what's next, blockers and decisions. A session can be deleted at any moment, so never rely on "updating at the end": keep `STATUS.md` current **while** you work.

| File | Purpose |
|---|---|
| [`docs/roadmap/STATUS.md`](docs/roadmap/STATUS.md) | **Where we are and what to do next.** Single source of truth for progress. |
| [`docs/roadmap/ROADMAP.md`](docs/roadmap/ROADMAP.md) | The plan: phases, epics, tasks (`P<phase>-<epic>.<n>`), acceptance criteria, as a checklist with a Progress table: the at-a-glance view of what is done, in progress and to do. Detail stays in `STATUS.md`. |
| [`docs/roadmap/WORKING-AGREEMENT.md`](docs/roadmap/WORKING-AGREEMENT.md) | Branching, definition of done, safety rails |
| [`docs/roadmap/ADRs/`](docs/roadmap/ADRs/README.md) | Architecture decisions. Implement only **Accepted** ones. |
| [`docs/audit/`](docs/audit/SUMMARY.md) | Audit findings by ID. `docs/audit/modules/<module>.md` lists each module's open defects and definition of done. |

**Resuming ("continue", or any new session):**
1. Read `STATUS.md`. If there is an **Active task**, its **Next step** is where to pick up. Otherwise take the first **Up next** task whose blockers are clear.
2. Check it against reality, because the last checkpoint may be one step behind. Run `git branch --show-current`, `git status --short` and `git log --oneline -5`. If git shows work that `STATUS.md` doesn't mention (uncommitted files, newer commits), work out what was done, update `STATUS.md` first, then continue.
3. Read the task's entry in `ROADMAP.md`, the ADRs it links, and the module report(s) for the code it touches.
4. Tell the user which task and step you are resuming and your plan. Wait for go-ahead on multi-file or design changes.
5. If the task needs something listed under "Waiting on Emmanuel", ask instead of guessing.

**Checkpoint: update `STATUS.md` immediately whenever any of these happens:**
- **Starting a task:** set the Active task, branch, state, and a step checklist with the **Next step** marked. In `ROADMAP.md`, mark the task `- [ ] 🔄`.
- **Finishing a step:** tick it, note the files touched or the commit, and move the **Next step** marker.
- **Running tests:** record the command and the result under "Last test run".
- **Committing:** record the hash on the step.
- **Getting blocked, or making or receiving a decision:** add it to "Waiting on Emmanuel" or "Decisions log".
- **Completing a task:**
  - Clear the Active task.
  - Update the epic progress counts and the repro-test count.
  - Move the task off "Up next".
  - In `ROADMAP.md`, tick the task (`- [x]`, commit hash in brackets), add `✅ complete` to its epic heading when every task is ticked, and update the Progress table counts.
  - In each fixed finding's module report, mark the finding `Fixed in <commit>`, and change the verdict if the module's definition of done is met.

Make each checkpoint a small edit to `STATUS.md` in the same turn as the work, never batched for later. Before starting a long-running command, make sure `STATUS.md` already says what you are about to do.

**Scratch files:** put any file that should not be in git in `tmp/` (it is gitignored). That covers notes, raw tool output, experiments and exports. Never leave scratch files elsewhere in the repo.

## Non-negotiables

These describe what the code enforces today. ADR-0004 (money) and ADR-0014 (order state machine) are still Proposed and will replace some of them.

- **Variant = SKU (ADR-0003):** price, stock, SKU and barcode live on `Variant`; every product has at least one (a default variant without options). Carts, orders, stock levels, reservations and stock movements reference `variantId`. Product attributes and variant option values are checked by the pure `src/product-types/domain/attribute-validation.ts` against the product type.
- **Stock (ADR-0008):** lives in `StockLevel` (variant, location: `onHand`, `reserved`; available = onHand - reserved). Change it only through `StockLedgerService` (`src/inventory/stock-ledger.service.ts`) on the caller's transaction (a location parameter, default the store's default `StockLocation`): every change is one conditional `StockLevel` update plus one append-only `StockMovement` (a trigger refuses updates and direct deletes). Orders reserve at placement (`StockReservation` ACTIVE), consume on online payment success or COD dispatch (`SHIPPED`), and release on cancel/expiry; each transition is a conditional update on the reservation status, so repeats are no-ops. Never write an absolute quantity. The database rejects negative onHand/reserved and reserved > onHand. Crossing a variant's low-stock threshold (on available summed over active locations) records `inventory.low_stock.v1`.
- **Locations and fulfilment (P4-A.1, `src/inventory/locations/`, pure rule in `src/inventory/fulfilment-location.ts`):** staff manage `StockLocation`s (`inventory.location.manage`, Owner and Manager); one default per store, always active (CHECK); a location with stock history cannot be deleted, only deactivated (never chosen, stock hidden from customers; existing reservations carry on). Each `ShippingZone`/`PickupLocation` has an ordered list (`ShippingZoneStockLocation`/`PickupLocationStockLocation`); empty or all inactive = the default. Placement locks the cart's `StockLevel` rows at the candidates (`StockLocationsService.lockFulfilmentLocation`, `FOR UPDATE` in a fixed order), picks the first location that fills every line and reserves the whole order there (`Order.stockLocationId` + reservations); none: `BAD_REQUEST`. Customer availability (`Variant.available`, cart, `totalStock`, `inStock` filter and field) is the best single serving location (`SERVING_LOCATION` in `serving-locations.ts`: active and listed somewhere, or the default), never the sum; checkout checks against the zone's/pickup point's candidates. Returned goods restock at the order's location.
- **Stock transfers (P4-A.2, `src/inventory/transfers/`):** `StockTransfer` + lines, machine in `stock-transfer-rules.ts` (DRAFT → DISPATCHED | CANCELLED; DISPATCHED → RECEIVED | PARTIALLY_RECEIVED, final). Each step claims the transfer with a conditional status update (loser: `CONFLICT`). Dispatch takes the lines off the source's available stock (`StockLedgerService.transferOut`, `TRANSFER` movement, all or nothing); in transit the units are on the lines, at no location. Receipt adds what arrived (`transferIn`); a shortfall is the line's variance with a required note, no movement. Cancel only before dispatch. Writes need `inventory.transfer` (Owner, Manager, InventoryClerk), reads `inventory.view`; audited.
- **Stock adjustments (P4-B.1):** a manual change is `adjustVariantStock` (signed delta at a location, default the store's default location) with a `StockAdjustmentReason` (`src/inventory/stock-adjustment.ts`: DAMAGED/LOST/EXPIRED only remove, FOUND only adds, CORRECTION/OTHER either way, OTHER needs a note, STOCK_TAKE only from an approved stock-take), stored as `StockMovement.adjustmentReason` (a CHECK allows it on ADJUSTMENT movements only) through `StockLedgerService.adjustAt`.
- **Stock-takes (P4-B.1, `src/inventory/stock-take/`):** a count session per location (`StockTake`, one `StockTakeLine` per variant in scope; at most one OPEN/SUBMITTED per location) through the pure machine `stock-take-status.ts` (OPEN → SUBMITTED → APPROVED, CANCELLED before approval; conditional updates on the session row). Expected = onHand + units sold (reservation CONSUMED) but not dispatched; read at open and again with each count, so stock moving during the count is no variance. Approval (`inventory.stocktake.approve`, Owner/Manager) posts each non-zero variance as an ADJUSTMENT (`STOCK_TAKE`, ref `StockTake`) in one transaction; a shortage below reserved refuses it (`CONFLICT` + `STOCK_TAKE_BELOW_RESERVED`). Expected quantities and variances are hidden from counters (field middleware).
- **Low-stock digest (P4-B.2, `src/inventory/low-stock/`):** the notifications consumer stores each `inventory.low_stock.v1` as a PENDING `LowStockAlert` (one per variant and location, partial unique index; `eventId` unique, so redelivery is a no-op). The maintenance job `inventory.low-stock-digest` (every 3 h, 06-21 UTC) locks the pending alerts, drops those whose variant recovered above its threshold (pure `low-stock-digest.ts`), marks the rest SENT with a digest id and records one `inventory.low_stock_digest.v1` per active staff member holding `inventory.alerts` (Owner, Manager, InventoryClerk) in the same transaction; the sender emails the digest (one section per location). No full-catalogue low-stock scan exists.
- **Lots and expiry (P4-C.1, `src/inventory/lots/`, pure rules in `lots.ts`):** opt-in per product (`Product.trackLots`); untracked products have no lot rows and `StockMovement.lotId` null. A `Lot` (variant, `lotNumber` unique per variant, `expiresAt`, optional `manufacturedAt`) holds units per location in `LotStock` (CHECK onHand >= 0); for a tracked variant the lots at a location add up to `StockLevel.onHand`. `StockLedgerService` does it: for a tracked variant every on-hand change locks the level then its lots, updates the level once and writes one movement per lot (`lotId`; a CHECK keeps lots off RESERVE/RELEASE). Increases need the lots (`receive`/`receiveLots`/`transferIn`/`adjustLots` with `lots`; `LotsService.receiveIntoLot` is the receipt path P4-E reuses: lot number + expiry in the future, an existing lot number adds to it with the same expiry); decreases draw the lots named or FEFO (`fefoDraw`: unexpired earliest expiry first, ties oldest; SALE then falls back to expired lots with a warning, TRANSFER never ships expired units nor what the reservations there need, removals then take expired). Reservations stay per variant and location; a cancelled paid sale goes back into the lots the order drew (`orderLotDraws`). Return restock: the lot named or the order's drawn unexpired lots. Transfers carry the lots of their dispatch movements; a shortfall falls on the latest-expiring lots (`assignTransferReceipt`). Stock-takes count per variant: shortage FEFO, surplus into the latest-expiring lot (none: `CONFLICT` + `STOCK_TAKE_NO_LOT`). Expired lots are unsellable: `expiredLotUnitsSql` is subtracted by placement (`lockLevels`, and the RESERVE guard in `applyEffect`), `Variant.available`, `totalStock` and the cart and checkout-quote checks (`sellableLevels` over `findExpiredLotUnits`, read only for lot-tracked variants); the hourly `inventory.expire-lots` job (advisory lock `70_412_007`) writes them off as ADJUSTMENT `EXPIRED` (ref `Lot`) up to the units not reserved and warns about the rest. `trackLots` switches only with no stock on hand, in transit or sold awaiting dispatch (product row `FOR UPDATE`; the ledger reads it `FOR SHARE`). `createProduct`/`createVariant` refuse opening stock for tracked products. Staff read `expiringStock` (1-365 days, default 30, per location/category, value at current price) and `variantLots` with `inventory.view`; lot receipts and adjustments use `inventory.adjust`, audited with the lots.
- **Serial units (P4-D.1, `src/inventory/serials/`):** opt-in per product (`Product.trackSerials`, plus `serialFormat` FREE_TEXT | IMEI (15 digits, Luhn) and `warrantyMonths`); untracked products are unchanged and refuse `serials`. One `SerialUnit` per physical unit (serial normalised by `serial-format.ts`, unique per variant; status IN_STOCK, ASSIGNED, SOLD, IN_TRANSIT, WRITTEN_OFF by the pure table in `serial-rules.ts`; CHECKs tie `locationId`/`orderItemId`/`soldAt`/warranty to the status) with an append-only `SerialUnitEvent` per change (trigger; carries the stock movement id). Every stock path of a tracked variant names one serial per unit through `SerialUnitsService` on the caller's transaction, next to its ledger movement: receipt (new serials, `SERIAL_ALREADY_KNOWN`), return restock (units SOLD on that order), adjustments (removal: IN_STOCK there → WRITTEN_OFF; addition: new or WRITTEN_OFF), transfers (dispatch → IN_TRANSIT, receipt → IN_STOCK, missing → WRITTEN_OFF). Unit moves are conditional updates on status (and location), so two requests never take the same unit (`CONFLICT` + `reason: SERIAL_NOT_AVAILABLE`). Staff (`order.fulfil`) assign units at pick per shipment line (`OrderSerialsService`, `SerialUnit.shipmentItemId` + `orderItemId`, CHECK: set while ASSIGNED/SOLD; shipment PICKING or PACKED, at the order's location, order row locked); a shipment's dispatch is refused (`BAD_REQUEST` + `reason: SERIALS_NOT_ASSIGNED`) until each of its serialised lines has exactly its quantity, then those units are SOLD; order cancel/expiry and shipment cancel free them; the shipment's delivery (`updateShipmentStatus` DELIVERED or `recordCodPayment`) starts their warranty. Invariant (nightly reconciliation, kind `SERIAL_UNITS`, report-only): per tracked variant and location, IN_STOCK + ASSIGNED units = onHand + units sold online not yet in a dispatched shipment (the stock-take's expected quantity; per order line, `UNDISPATCHED_RESERVED_UNITS` in `src/inventory/awaiting-dispatch.ts`). Stock-takes refuse to approve a variance on a tracked variant (`STOCK_TAKE_SERIAL_VARIANCE`). `trackSerials` turns on only with no untracked stock (on hand, in transit, open orders) and off only with no unit IN_STOCK/ASSIGNED/IN_TRANSIT; tracked variants take no opening stock. Lookup by serial: `serialUnitLookup` (`order.view`); customers see `OrderItem.serials` on their own orders.
- **Purchasing and cost (P4-E.1, `src/purchasing/`):** `Supplier` (name unique per store ignoring case via `nameKey`; store currency only; deactivated, never deleted, once a purchase order refers to it). `PurchaseOrder` (reference `PO-<number>` from a sequence) + `PurchaseOrderLine` (quantity ordered, tax-exclusive `unitCost` Decimal(14,4), quantity received; CHECK received <= ordered) through the pure machine `purchase-order-status.ts` (DRAFT → SENT | CANCELLED; SENT → PARTIALLY_RECEIVED | RECEIVED | CANCELLED; PARTIALLY_RECEIVED → itself | RECEIVED | CLOSED (closed short); no approval). Every change locks the order row then moves the status with a conditional update (loser: `CONFLICT`); lines, supplier and location change only in DRAFT; sending only stamps `sentAt` (no supplier email yet). `receivePurchaseOrder` (`purchase-order-rules.ts` `receiptPlan`: each line at most its outstanding units, no tolerance, `BAD_REQUEST`) writes one `PurchaseOrderReceipt` + lines and, per line in variant order, folds the units into the cost, then adds them at the order's location as RECEIPT movements (`refType` PurchaseOrder, `StockMovement.unitCost`; a CHECK allows it on RECEIPT only), lot-tracked through `LotsService.receiveIntoLot`, serial-tracked through `SerialUnitsService.receive`, and increments the line conditionally. Weighted-average cost (`VariantCostService`, pure `weighted-average-cost.ts`): store-wide `Variant.costPrice` Decimal(14,4), null = unknown; new = (onHand over all locations × old + qty × unitCost) / (onHand + qty), half-up to 4 dp; unit cost alone when old is null or onHand <= 0; variant rows locked in id order first. Each change is an append-only `CostChange` (trigger; source PURCHASE_ORDER, ref the receipt, or MANUAL via `setVariantCost`: opening cost or a correction, with a reason; later receipts average from it). No other stock path changes cost; cost never reaches pricing. Cost fields (`Variant.costPrice`, `StockMovement.unitCost`, PO costs, receipt values, cost values on `stockTakeVarianceReport` and `expiringStock`) are nullable and hidden without `inventory.cost.view` (`COST_VIEWERS_ONLY` field middleware); `variantCostHistory` needs it. Permissions: `purchasing.view` and `purchasing.receive` (Owner, Manager, InventoryClerk), `purchasing.manage` and `inventory.cost.view` (Owner, Manager); no step-up. Audited (`Supplier`, `PurchaseOrder` with receipt lines incl. lot numbers and serial counts, `Variant` for a manual cost).
- **Order, payment and fulfilment status** (ADR-0014, P1-O.2) change only through their pure transition tables: `src/order/order-status.ts` (PLACED → CONFIRMED → IN_FULFILMENT → COMPLETED; CANCELLED, EXPIRED, PAYMENT_REVIEW), `src/payment/payment-intent-status.ts` (the PaymentIntent carries the order's payment: PENDING → CAPTURED → PARTIALLY_REFUNDED/REFUNDED; FAILED, CANCELLED) and `src/order/shipment-status.ts` (per shipment; PENDING/PICKING/PACKED → CANCELLED before dispatch). Order moves go through `OrdersRepository.transitionStatus` / `transitionOrder` (`src/order/order-transition.ts`): row lock, conditional `updateMany`, `OrderStatusEvent` in the same transaction; shipments through `transitionShipment` (with `ShipmentStatusEvent`). Never a plain status update. Staff never set an order status directly: payment confirms, the first step of any shipment starts fulfilment, delivery of the last units or `recordCodPayment` completes. COD stock is consumed on dispatch (OUT_FOR_DELIVERY / READY_FOR_PICKUP).
- **Split shipments (P5-B.1, `src/order/shipments.service.ts`, pure rules in `shipment-allocation.ts`):** an order has zero or more `Shipment`s, each with immutable `ShipmentItem`s (order line, quantity). Staff (`order.fulfil`) create them from the unshipped units (`createShipment`, default everything; `CONFLICT` + `SHIPMENT_QUANTITY_EXCEEDED` / `NOTHING_TO_SHIP`), cancel one before dispatch (`cancelShipment`: units unshipped again, picked serials back on the shelf), move one (`updateShipmentStatus`/`updateShipping` take a shipment id) and list them (`orderShipments`, `order.view`); all under the order row lock, audited. A trigger (`ShipmentItem_within_order`) keeps a line's units over non-cancelled shipments within the ordered quantity and the line on the shipment's order. An online order completes when no shipment is open and every unit is in a DELIVERED shipment or refunded (non-failed `RefundLine`s), checked at each final shipment step and shipment cancel. A COD order is never split (`BAD_REQUEST` + `COD_ORDER_NOT_SPLIT`: one cash collection = one delivery), so its dispatch consumes the whole order. Order cancel cancels the shipments not yet dispatched and is refused once any shipment left (staff then cancel the rest and `refundOrder`). Rider and proof of delivery attach to `Shipment` later (P5-C).
- **Customer tracking (P5-B.2):** `Order.trackingTimeline` (`OrderTrackingResolver`, pure merge in `src/order/tracking-timeline.ts`): order and shipment status events by time, with each shipment's carrier/tracking number, no actor or reason; polling only, on the customer's own order (order queries are scoped). SMS milestones: the notifications consumer of `shipment.status_changed.v1` queues `sms.shipment_milestone.v1` (ids only, job id `<eventId>-sms`, so a re-run event queues it once and the sent marker keeps it to one send) for OUT_FOR_DELIVERY and DELIVERED (READY_FOR_PICKUP belongs to the pickup flow); the job reads the shipment and sends through `SmsSender` to the verified account phone, else the delivery address snapshot phone, else the contact phone (Ghana numbers, `src/notifications/sms/shipment-sms.ts`; none: skipped with an ids-only warning). No guest tracking lookup.
- **Payment providers (ADR-0007 §1):** payment services, webhook processing, reconciliation and refunds reach a provider only through the `PaymentProvider` port (`src/payment/providers/payment-provider.port.ts`: `initialize`, `verify`, `refund`, `parseWebhook(rawBody, headers)`, `settlesPayment`, `listTransactions`, `capabilities`), resolved by `PaymentProviderRegistry.get(provider)` from the attempt's `provider`. Adapters: `PaystackAdapter` (over the thin `PaystackClient`; raw-body HMAC with `timingSafeEqual`) and `CashOnDeliveryAdapter` (no provider operations). `PaymentProvidersModule` is its own module so `OrderModule` and `ReturnsModule` can use it.
- **Store payment config (P3-A.2, `src/payment/settings/`):** Paystack keys live per store in `PaymentProviderConfig`, the secret AES-256-GCM encrypted with `PAYMENT_CONFIG_ENCRYPTION_KEY` (random IV, `"<storeId>:<provider>"` as AAD); reads show only the last 4, audits and logs never the secret. `PaymentSettingsService` resolves credentials on every call (no cache, so API and worker see a change at once): the DB config, else `PAYSTACK_SECRET_KEY` (+ `PAYSTACK_CALLBACK_URL`), else none (online payment refused, checkout calls 503, webhooks 401). Payment methods are `Store` columns (card, mobile money, COD on/off; provider per online method, CHECK: never COD). The order keeps `PaymentMethod` ONLINE | CASH_ON_DELIVERY; the online method (`OnlinePaymentMethod` CARD | MOBILE_MONEY) is chosen per attempt at `POST /payment/initialize`, stored as the attempt `channel` and sent to Paystack as `channels`. `checkoutQuote`/`createOrder`/initialize refuse a method not on offer with `BAD_REQUEST` + `reason: PAYMENT_METHOD_UNAVAILABLE`. Changes need `payment.settings.manage` (Owner only) and step-up.
- **Cash on delivery (P3-B.1/B.2, `src/phone-verification/`, `src/cod/`):** COD needs the account's phone verified by SMS code: `PhoneVerificationService` stores a 6-digit code as an HMAC (key derived from `MFA_ENCRYPTION_KEY`, bound to user and phone) in Redis under hashed keys (`PhoneOtpStore`, Lua: 10-minute TTL, 5 attempts, 60 s resend cooldown, 5 codes/day per phone, 10/day per account; `OTP_RATE_LIMITED`); the SMS goes out from the worker (`sms.phone_otp.v1` on the notifications queue → `SmsSender` → `SmsProvider` port, Hubtel adapter over fetch; no provider: skipped with a masked log outside production, refused in production). Verified = `User.phoneVerifiedAt` set and `phoneVerifiedNumber` = `phoneNumber`; a DB trigger clears both when `phoneNumber` changes. `CodRiskService` runs the gates (pure `codRefusal` in `cod-risk.ts`): store offers COD, phone verified (`PHONE_NOT_VERIFIED`), blacklist (`CodBlacklistEntry`, normalised phone / GPS code / street|city; `cod-blacklist.ts`), zone `codEnabled` (pickup exempt), open COD orders per verified phone (`Store.codMaxOpenOrdersPerPhone`, counted by `Order.codPhone` or the account), grand total cap (`Store.codMaxOrderTotal`); refusals are `COD_NOT_AVAILABLE` + `codReason` and `cod_gate_refusals_total{gate}`. `checkoutQuote.cashOnDelivery` reports it; `createOrder` checks it in the order transaction after a per-phone advisory lock. Settings and blacklist under `payment.settings.manage` + step-up, audited.
- **COD cash (P3-B.3, `src/payment/cash/`):** `recordCodPayment` (`payment.record`) names who took the cash (`CashCollection.riderId`: for a delivery a rider (P5-C.1, `assertCollector`), at the pickup counter any active staff member; older collections by other staff stay valid) and `collectedAt` (not in the future nor before dispatch); the amount must equal `grandTotal` (no short collections: payment and order transitions are unchanged). Riders hand cash in as a `CashRemittance` (`recordCashRemittance`, `cod.cash.manage`: Owner, Manager, Cashier) covering some of their unremitted collections: the collections are row-locked in id order and linked with a conditional update (`remittanceId IS NULL`), so a collection is remitted once and a racing remittance gets `CONFLICT` + `reason: COLLECTION_ALREADY_REMITTED`. `discrepancy` = amount - sum of the collections (negative short, positive over; pure rules in `cash-remittance.ts`) needs a note (`DISCREPANCY_NOTE_REQUIRED`; also a CHECK); it records `cod.remittance_discrepancy.v1` and the `cod_remittance_discrepancies_total` metric. Remittances are immutable (triggers refuse update and delete; a correction is a new remittance, possibly with no collections), and a collection only ever changes by getting its `remittanceId` once. `codCashReport` (pure aggregation in `cash-report.ts`) gives per rider for `[from, to)` collected, outstanding, remitted and short/over, plus COD orders delivered with no collection.
- **Riders (P5-C.1, `src/delivery/`, pure rules in `rider-assignment.ts`):** a rider is an active staff member whose role lists `delivery.ride` (system Rider role, not mfaRequired; never the Owner). Staff with `order.fulfil` assign/unassign a rider to a delivery shipment (`Shipment.riderId` + `assignedAt`, CHECK both or neither) under the order lock: first rider before dispatch or after a failed attempt, reassign after dispatch only with a reason, no unassign while OUT_FOR_DELIVERY; audited `RIDER_ASSIGN`/`RIDER_UNASSIGN`. Riders (`delivery.ride`) read only their own shipments as `RiderDelivery` (recipient, address, items, cash to collect) and step them through `ShipmentsService.moveAsRider` (PACKED/FAILED_DELIVERY → OUT_FOR_DELIVERY, OUT_FOR_DELIVERY → FAILED_DELIVERY); another rider's shipment is NOT_FOUND. `Shipment.rider`/`assignedAt` are staff-only fields.

- **Autocomplete and synonyms (P6-S.4, `src/products/search/synonyms/`):** `searchSuggestions(prefix, first 1-10)` (public, optional sign-in, global throttler) via `ProductSearch.suggest`: one statement (`suggestionQuery`) over published products and brands/categories having one, name `ILIKE %prefix%` (wildcards escaped) or `prefix <% name` (fuzzy threshold), starts-with first then word similarity; under two letters or digits returns empty lists without a query. `SearchSynonym` groups (TWO_WAY: terms find each other; ONE_WAY: `term` finds `synonyms`; CHECKs on shape; pure rules and `expandSearchText` in `synonym-rules.ts`): the adapter reads all groups (max 500, not cached, so every instance sees a change at once) and ORs `websearch_to_tsquery` over at most 8 variants of the text with whole-word substitutions (negated terms and OR left alone); the fuzzy fallback uses the original text only. Reads `catalog.product.read`, writes `catalog.taxonomy.write` (reused: synonyms are catalogue vocabulary), audited.
- **Reviews (P6-V.1, `src/review/`, pure rules in `review-rules.ts`):** only a verified buyer reviews (`verifyingLine`: an order line of theirs for the product with a unit in a DELIVERED shipment, or a COMPLETED order, not fully refunded by non-FAILED refunds; else `FORBIDDEN` + `REVIEW_NOT_VERIFIED_PURCHASE`); the review keeps that `orderItemId` and `verifiedPurchase` (false on older reviews). One per (user, product): unique index, checked under the product row lock (`CONFLICT` + `REVIEW_ALREADY_EXISTS`). Published at once; title <= 120, comment <= 2000, trimmed; the author edits (null clears, `editedAt`) and hard-deletes. Photos: `POST /reviews/:reviewId/photos` (own review, image checked by its bytes, Cloudinary `reviews/<reviewId>/`, at most 4 under the review row lock, `REVIEW_PHOTO_LIMIT`). Customers report once per review (`ReviewReport`, `ALREADY_REPORTED`); staff with `review.moderate` (Owner, Manager, Support) read `reportedReviews` (open reports), hide/unhide with a reason (`ModerationStatus`; hiding closes the open reports), dismiss reports and set the public reply, all audited. Hidden reviews leave every public read and the rating; the author sees them in `userReviews`; `hiddenReason` is staff-only (field middleware). `Product.ratingCount`/`ratingAverage`/`rating1Count`..`rating5Count` are recomputed from the PUBLISHED reviews by `ReviewRepository.refreshRating` (raw update, so `Product.updatedAt` stays) in the same transaction as every create/edit/delete/hide/unhide, after `lockProduct`; exposed as `Product.rating`. Public reads (`productReviews`, `review`, `Product.reviews(first)`) are `@Auth(AuthType.Optional)`: published reviews of public products only, keyset-paged by review id (`first` + `after`). Review and report writes use the `contentWrite` throttler (10/min).
- **Product Q&A (P6-V.2, `src/product-questions/`):** a signed-in customer asks about a public product (`ProductQuestion`, body 5-1000); staff with `review.moderate` answer (one store answer per question, replaceable, audited); verified buyers do not answer. A question is public once answered and PUBLISHED (`productQuestions`, `productQuestion`: `@Auth(AuthType.Optional)`, keyset-paged, latest answer first); the asker sees their own in `myProductQuestions`, staff the `unansweredProductQuestions` and `reportedProductQuestions` queues. Reports (`ProductQuestionReport`, one per customer), hide/unhide (closing open reports) and dismiss reuse the review rules (`review-rules.ts`) and inputs, each under the question row lock and audited. The asker is a `PublicProfile` only.
- **Recently viewed (P6-G.3, `src/recently-viewed/`):** signed-in users record views explicitly (`recordProductView`, public products only, `productView` throttler 60/min); one `RecentlyViewedProduct` row per (user, product), upserted and pruned to the latest `RECENTLY_VIEWED_LIMIT` (20) in one transaction under a per-user advisory lock, so concurrent views never leave more. `recentlyViewed(limit)` returns the still-public products, latest first. Guests keep their list client-side.
- **Notifications (P6-N.1, ADR-0015, `src/notifications/`):** every email/SMS text comes from the template registry `templates/templates.ts` (key + version, category, per-locale channel variants: email subject/HTML/text, SMS (refused above 306 chars; free text `clip`ped), in-app title/body; `en` only). Email HTML is built only with the `markup` tag (`templates/render.ts`), which escapes every interpolated value (not named `html`: Prettier would reformat it as HTML); money via `formatMoney` (GHS, 2 dp); orders by order number. `NotificationDispatcher.deliver` is the only send path: it finds/creates the `Notification` row by `dedupeKey` (event job id + channel, or `direct:<uuid>` written by `NotificationsService` when queueing a direct job), sends nothing for a SENT/SKIPPED row, checks consent at send time (pure `preferences/notification-preferences.ts`: TRANSACTIONAL always; MARKETING only with the channel's `NotificationPreference` enabled, SMS also a verified phone) and marks SENT (provider message id) / SKIPPED (`NO_CONSENT`, `NO_ADDRESS`, `NOT_CONFIGURED`) / FAILED (`PROVIDER_ERROR`, rethrown so the job retries). Preferences: `myNotificationPreferences`/`updateNotificationPreference` (Bearer), staff `recordCustomerConsent` (`user.manage`) and `customerConsentHistory` (`user.view`); each marketing change writes the preference and an append-only `ConsentEvent` (trigger) under a lock on the user row. The password-reset email links to `FRONTEND_URL/reset-password#token=...`. In-app feed (P6-N.4, `customer/in-app-feed.*`): the dispatcher delivers channel IN_APP by storing title/body/`refType`+`refId` on the row (CHECK: a SENT in-app row has text; only in-app rows have `readAt`); the sender adds feed entries for order placed, payment received, out for delivery, delivered, ready for pickup and refund sent (dedupe `<jobId>:IN_APP`). `myNotifications` (cursor = last id, newest first), `unreadNotificationCount`, `markNotificationsRead(ids)`, `markAllNotificationsRead`: Bearer, always scoped to the caller. Maintenance job `notifications.purge` (03:15 UTC, advisory lock `70_412_008`) deletes in-app rows after 90 days and email/SMS rows after 180. SMS (P6-N.2): every SMS (OTP, shipment milestones with the delivery code, ready for pickup) goes through the dispatcher, which stores the provider message id and `providerStatus` (Hubtel's status code) and counts `sms_messages_total`. The Hubtel response schema and its delivery reports could not be verified (docs unreachable), so the adapter reads the response defensively and there is no delivery-status webhook.
- **Saved carts and abandoned-cart reminders (P6-G.2, `src/cart/saved-items.*`, `src/cart/abandoned/`):** `SavedCartItem` (one per user and variant, CHECK quantity > 0, limit 100): `saveCartItemForLater` moves a cart line there in one transaction, `moveSavedItemToCart` goes through `CartService.addToCart` (sale and stock checks) then deletes the saved row; never touches pricing. The hourly maintenance job `cart.abandoned-reminders` (:20 UTC, advisory lock `70_412_009`) applies the pure `abandonedCartDecision` (lines idle between `Store.abandonedCartReminderDelayHours` (1-72, default 4) and 7 days, no order since the last change, marketing consent on a reachable channel, state hash `cartStateHash` never reminded (unique `AbandonedCartReminder(userId, cartStateHash)`), none in the last 7 days) and records the reminder + `cart.abandoned_reminder.v1` in one transaction; the worker sends template `cart.abandoned` (MARKETING) by email and SMS (verified phone) through the dispatcher, which re-checks consent. Marketing emails carry `MarketingLinks.unsubscribeUrl` (HMAC token keyed from `MFA_ENCRYPTION_KEY`, no expiry); public `unsubscribeMarketingEmail(token)` withdraws email consent with source EMAIL_LINK.
- **Bulk imports and exports (P8-I, `src/imports/`, `src/exports/`):** staff upload CSV (UTF-8, comma or semicolon) or .xlsx over REST (`POST /imports/products|prices|stock`, multer memory, 10 MB, `413` above); the bytes are sniffed (`spreadsheet/file-format.ts`: .xlsx = zip with `xl/workbook.xml` and no VBA, else UTF-8 text = CSV; never the extension) and stored privately as `ImportJob.file` (bytea, cleared once validation has parsed it; `imports.purge` maintenance job deletes jobs after 30 days). `ImportJob` status through the pure table `import-job-status.ts` (QUEUED → VALIDATING → VALIDATED → APPLYING → COMPLETED; FAILED; CANCELLED from QUEUED/VALIDATED; FAILED → APPLYING re-runs an apply), every move a conditional update. The `imports` queue (worker only, `ImportsProcessor`): `import.validate` (`ImportValidator`: `readTable` (csv-parse / read-excel-file, numbers kept as text), header check per kind, pure per-kind rules in `kinds/` (`planProductGroup`, `planPriceRow`, `planStockRow`) against facts loaded in bulk (`ImportFactsRepository`), one `ImportRow` per data row with errors/warnings/action; nothing changes) and `import.apply` (`ImportApplier`: VALID rows in batches of whole units (a product's rows, else one row; `applyBatches`), each batch one transaction that re-plans every unit from facts read (and SKUs/levels locked) inside it; a refused unit rolls the batch back, its rows become FAILED and the batch retries without it; a row leaves VALID by a conditional update in the batch, so a retried job never applies it twice). PRODUCTS: keyed by SKU (case-insensitive), new products grouped by `product_key`, attributes/options checked by `attribute-validation.ts`, categories/brands/tags by name (never created), existing prices/type/`is_taxable` never changed, writes audited per product with the job id. PRICES: `base_price` only (price derived as everywhere), `PriceChange` source `IMPORT`; upload and `applyPriceImport` need step-up. STOCK: `delta` with a manual reason or `count` (delta = count − on-hand under the level row lock, default CORRECTION), through `StockLedgerService.adjustAt` (`refType` ImportJob); lot/serial-tracked variants refused per row. Permissions: `catalog.import` (Owner, Manager), `inventory.import` and `catalog.export` (Owner, Manager, InventoryClerk); job reads/apply/cancel are GraphQL per domain (`catalogImportJob(s)`, `stockImportJob(s)`, `applyProductImport`/`applyPriceImport`/`applyStockImport`, `cancelCatalogImport`/`cancelStockImport`); upload, apply and cancel audited (`ImportJob`). Exports are synchronous REST downloads (`/exports/products|stock` `catalog.export`, `/exports/orders` `order.view`, `/exports/orders/with-customers` + `customer.data.export` + step-up), at most 50,000 rows, audited `EXPORT`. Every CSV/XLSX the API writes goes through `table-writer.ts` `escapeFormula` (= + - @ tab CR prefixed with `'`, plain numbers left alone).
- **Side effects** (email, webhook processing) run in the worker, never on the request path. After a state change, write an outbox event in the same transaction (`OutboxService.record(tx, ...)`); for an email with no surrounding transaction, use `NotificationsService` (it queues the job). Consumers are idempotent on the job id; errors and logs carry no addresses or tokens.
- No secrets or PII in logs.
- **Migrations:** create with `--create-only` and review the SQL. Never edit an applied migration. Backfills must be safe to re-run. `prisma migrate diff` must show no drift.
- **API changes:** regenerate `schema.gql` with `npm run schema:generate` and commit it (CI fails on a stale file). Update `FRONTEND_API_DOCUMENTATION.md` with every API change. CI's graphql-inspector check fails on breaking changes unless a commit in the push/PR is marked `[breaking-api]`.
- **No API clients yet (Emmanuel, 2026-11-20):** no frontend or other client uses this API, so breaking changes are allowed without deprecation windows or compatibility shims: choose the clean design. Still mark such commits `[breaking-api]` and list the breaks in `FRONTEND_API_DOCUMENTATION.md`. This ends when the first frontend or client integrates; from then on, deprecate before removing.

## Architecture

**NestJS** backend with **GraphQL** (Apollo Server v5, Express 5) as the primary API. REST endpoints exist only for payment webhooks (Paystack). The GraphQL schema is auto-generated to `schema.gql` on startup.

**Database:** PostgreSQL via **Prisma 7** ORM with the `@prisma/adapter-pg` driver adapter. Schema lives in `prisma/schema.prisma`; CLI config (schema and migrations paths, seed command, `DATABASE_URL`) in `prisma.config.ts`, which loads `.env` itself. Import the client, `Prisma` and enums from `src/generated/prisma/client`, not `@prisma/client`. Migrations are in `prisma/migrations/`.

### Module structure

Each feature follows this pattern:
```
feature/
├── feature.module.ts
├── feature.service.ts        # Business logic, calls Prisma directly
├── feature.resolver.ts       # GraphQL queries/mutations
├── dto/                      # Input types and filter args (class-validator decorated)
├── entities/                 # GraphQL output types
└── enums/                    # Feature-specific enums
```

Feature modules: `users`, `products`, `product-types`, `categories`, `sub-categories`, `brand`, `tag`, `variant`, `cart`, `order`, `payment`, `addresses`, `promotions`, `customer-groups`, `price-lists`, `wishlist`, `review`, `returns` (returns and, in `refunds.module.ts`, refunds), `inventory`, `analytics`, `tax`, `shipping-zones`, `pickup-locations`, `price-history`, `fraud` (velocity checks), `phone-verification` (SMS codes), `cod` (cash-on-delivery risk gates), `purchasing` (suppliers, purchase orders, weighted-average cost), `delivery` (riders, proof of delivery), `guest-checkout` (guest carts, orders and access tokens), `loyalty` (points ledger, redemption facts, expiry; `LoyaltyLedgerModule` holds the ledger alone for checkout, completion and refunds), `referrals` (codes and referral entry; imported by `IamModule` for sign-up), `imports` (bulk CSV/Excel imports), `exports` (CSV/Excel exports).

Supporting modules: `prisma` (PrismaService), `config` (Joi env validation in `env.validation.ts`, cache config), `currency`, `notifications` (Resend email + templates), `health` (health controller/indicators), `redis` (shared ioredis client), `jobs` (BullMQ queues), `outbox` (domain events + relay), `worker` (the `ROLE=worker` root module), plus `instrument.ts` (main.ts's first import: starts Sentry, then `telemetry.ts`: one OpenTelemetry NodeSDK for traces, enabled via `OTEL_ENABLED`, and Prometheus metrics) and `observability/` (Sentry options and PII scrubbing, `reportError`/`reportFailedJob`, `AppMetrics`, the HTTP metrics middleware and the GraphQL metrics plugin).

### Authentication & Authorization (`src/iam/`)

- **JWT**: Access token (1h) + Refresh token (24h) + password-reset token (15m, `JWT_RESET_SECRET`). TTLs are overridable via `JWT_*_TTL` env vars. Refresh rotation runs in a Prisma `$transaction`. All routes are protected by default via `AuthenticationGuard`.
- Mark public routes with `@Auth(AuthType.None)`. `@Auth(AuthType.Optional)` (public catalogue queries) is public but verifies a bearer token when one is sent and attaches its user; an invalid or expired token gets `UNAUTHENTICATED`, never the anonymous view.
- Mark staff routes with `@RequirePermission('order.refund', ...)` (ADR-0013; fulfilment steps need `order.fulfil`, cancel/delete `order.manage`) and customer self-service routes staff must not use with `@CustomerOnly()`. Mark routes open to any signed-in user with `@Auth(AuthType.Bearer)`.
- Roles are data: `StaffRole` (system roles Owner, Manager, InventoryClerk, Cashier, Support, Rider seeded by migration; Owner always holds every permission) assigned through one `StoreMembership` per user. `AccessTokenGuard` loads the membership with the user on every request (`request.access`, `@ActiveAccess()`); `AuthorizationGuard` enforces the policy. Staff-account and role changes follow `src/iam/authorization/staff-rules.ts` (no escalation, only an Owner acts on an Owner, the last Owner stays) and are audited.
- Social login: Google and Facebook via `GoogleAuthenticationService` / `FacebookAuthenticationService`, linked to users through the `AuthProvider` model.
- **MFA (`src/iam/mfa/`):** own RFC 6238 TOTP on `node:crypto` (SHA1, 6 digits, 30 s, ±1 step, replayed steps refused via `User.mfaLastUsedStep`); secrets AES-256-GCM encrypted with `MFA_ENCRYPTION_KEY` (user id as AAD), 10 single-use recovery codes stored as keyed hashes. `AuthenticationService.generateTokens` is the only way to start a session after a first factor and fails with `UNAUTHENTICATED` + `reason: MFA_REQUIRED` + a 5-minute `mfaChallenge` for MFA users (so password and social sign-in cannot skip it); `completeMfaSignIn` finishes it. Roles with `mfaRequired` (Owner, Manager) get `FORBIDDEN` + `reason: MFA_ENROLLMENT_REQUIRED` on every permission-guarded operation until enrolled.
- **Step-up:** mark sensitive resolvers `@RequireStepUp()` (optionally with an argument condition) next to `@RequirePermission`. Access tokens carry a session id (`sid`, kept across refresh); `stepUp`, `completeMfaSignIn` and `confirmMfaEnrollment` record a verification per session in Redis (`StepUpStore`, 10 minutes); otherwise `FORBIDDEN` + `reason: STEP_UP_REQUIRED`. Covered: role/permission changes, refunds, price changes (product/variant price, promotions and coupon codes, price lists, taxes, delivery rate rules), data exports (`addresses` without `userId`).
- e2e helpers: `prepareStaffAccounts` gives directly inserted ADMIN/SUPER_ADMIN users their membership and enrols Owner/Manager MFA with `TEST_TOTP_SEED`; `signInWithPassword` completes the second factor (fresh step-up).

### Commons (`src/commons/`)

- `LoggerService` — Winston-based logger, used app-wide: single-line JSON on stdout (ISO UTC `timestamp`, `level`, `message`, `context`, `requestId`, `userId`, `jobId`/`queue` in jobs, plus structured fields passed as the third argument); coloured text and rotated files under `logs/` in development only. Level via `LOG_LEVEL`. Stack traces only in development (`stackForLog`)
- `CloudinaryService` — image upload/storage (`upload.controller.ts` exposes the REST upload)
- `AuditService` — writes to the `AuditLog` model
- Global exception filter (`AllExceptionsFilter` + `error-classification.ts`) maps HTTP statuses to GraphQL codes (400 `BAD_REQUEST`, 401 `UNAUTHENTICATED`, 403 `FORBIDDEN`, 404 `NOT_FOUND`, 409 `CONFLICT`; ValidationPipe failures `BAD_USER_INPUT`) and Prisma P2002/P2003 → `CONFLICT`, P2025 → `NOT_FOUND` with safe messages; an HttpException whose response has `extensions` (e.g. `reason`) passes them on; stack traces are logged only in development
- GraphQL query limits (`commons/graphql/query-limits.ts`): depth ≤ 8, aliases ≤ 15, estimated cost ≤ 3000 (`graphql-query-complexity`); introspection is exempt and off in production
- `GqlThrottlerGuard` — global rate limiting (stricter limits on auth mutations such as `forgotPassword`/`resetPassword`)
- `PaginationArgs` / `PageInfo` entities are shared across all list queries

### Platform behaviour

- **Redis is required** in every environment (`REDIS_HOST`; startup fails without it). It backs the global `CacheModule` (5 min default TTL), the throttler storage (`RedisThrottlerStorage`, one Lua script, so limits hold across instances) and the shared ioredis client (`REDIS_CLIENT` from `src/redis/redis.module.ts`, closed on shutdown). `/health/ready` probes it with `PING`.
- **Two processes, one image:** `ROLE=api` (default) serves GraphQL/REST; `ROLE=worker` (`src/worker/worker.module.ts`, or `--role=worker`) runs the outbox relay and the BullMQ processors and serves only `GET /health/live` and `/health/ready` on `PORT`. Queue processors are registered only in `WorkerModule`, so the API never consumes jobs. Both shut down gracefully on SIGTERM.
- **Repeatable jobs:** the former crons are BullMQ job schedulers on the `maintenance` queue (`src/worker/maintenance-jobs.ts`), upserted by every worker at startup and run once per tick across the cluster; the tasks keep their Postgres advisory locks as a second guard. A worker removes the schedulers of jobs that no longer exist at startup. `inventory.reconcile-stock` (02:30 UTC) checks every `StockLevel` against the sum of its movements and its ACTIVE reservations and only reports (metric + warning log with ids); it never corrects. `inventory.low-stock-digest` (every 3 hours, 06:00-21:00 UTC) emails staff the variants that went low (P4-B.2). `inventory.expire-lots` (hourly at :05 UTC) writes expired lots off (P4-C.1). `cart.purge-guest-carts` (03:45 UTC) deletes expired guest carts (P6-G.1). `notifications.purge` (03:15 UTC) applies the notification retention (P6-N.4). `cart.abandoned-reminders` (hourly at :20 UTC) records abandoned-cart reminders (P6-G.2). `loyalty.expire-points` (00:50 UTC) expires unspent loyalty points (P6-L.1). The stock reconciliation also checks each lot against its movements and, for lot-tracked variants, the lots against the level (`LOT_MOVEMENTS`, `LOT_TOTAL`). There is no `@nestjs/schedule`.
- **Order events:** `order.placed.v1`, `order.status_changed.v2` (recorded for COMPLETED), `shipment.status_changed.v1` (dispatch and delivery, with `carrier` and `items` since P5-B.1), `shipment.tracking_updated.v1`, `payment.succeeded.v1`, `refund.succeeded.v1` (every processed refund; the customer is emailed), `return.status_changed.v1` (P6-R.1; logged for now), `payment.dispute_opened.v1`, `cod.remittance_discrepancy.v1` (logged with ids only); `order.status_changed.v1` and `order.shipment_updated.v1` are no longer recorded but still consumed until drained.
- **Queues:** `notifications` (outbox email events and direct email jobs; 6 attempts, exponential backoff from 5 s; sent-once marker per job id in Redis plus Resend idempotency key), `webhooks` (stored Paystack events, job id = `WebhookEvent` id; 8 attempts; the endpoint answers 200 once the event is stored), `maintenance` (repeatable jobs), `imports` (P8-I validation and apply runs; 3 attempts, exponential backoff from 10 s; the import job is FAILED once they are spent). Jobs that spend their attempts stay in the failed set (30 days) and are listed/retried by the SUPER_ADMIN `failedJobs` / `retryFailedJob` operations (audited).
- **Outbox (ADR-0009):** write a domain event with `OutboxService.record(tx, event)` inside the business transaction; event types are versioned (`src/outbox/domain-events.ts`). The worker's `OutboxRelay` publishes unpublished rows (`FOR UPDATE SKIP LOCKED`) to BullMQ with `jobId = event id`; consumers must be idempotent on that id.
- **Production safeguards:** GraphQL introspection is off when `NODE_ENV=production`; `ALLOWED_ORIGINS` is required at startup in production; helmet sets CSP and HSTS.
- **Correlation:** `LoggerMiddleware` keeps a client `X-Request-ID` matching `^[A-Za-z0-9-]{1,64}$` (else generates a UUID), echoes it in the response and runs the request inside an `AsyncLocalStorage` context (`src/commons/correlation.ts`), so every log record carries `requestId` (and `userId` once authenticated) without passing it around. Jobs carry it as `meta.requestId` in their data (`withJobMeta`; outbox rows store it in `OutboxEvent.requestId` and the relay copies it); processors run each job inside `runJobInContext` (requestId + jobId + queue; scheduled jobs get a fresh id).
- **Error tracking (Sentry):** on only when `SENTRY_DSN` is set, in both roles, initialised before the app. Reported: 5xx/`INTERNAL_SERVER_ERROR` from REST and GraphQL (`AllExceptionsFilter`, and `formatError` for errors the filter never saw), and BullMQ jobs with no attempts left; expected client errors (4xx, `BAD_USER_INPUT`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`) are not. Events carry `requestId`/`jobId`/`queue` tags and the user id only; `dataCollection` is all off and `scrubEvent` strips request bodies, headers, cookies, query strings and breadcrumbs. Use `reportError(exception)` for a caught server failure that must not vanish.
- **Metrics (Prometheus):** unless `METRICS_ENABLED=false`, each process serves `GET /metrics` from the OpenTelemetry Prometheus exporter's own server on `METRICS_PORT` (default 9464, all interfaces; never the API port, so do not expose it publicly). API: `http_request_duration_seconds` (method, route template, status class), `graphql_operation_duration_seconds` (operation name capped at 100 distinct names, type, outcome), `api_errors_total` (transport, code), `webhook_processing_failures_total`, `cod_remittance_discrepancies_total` (kind: SHORT, OVER), `delivery_code_failures_total` (result: WRONG_CODE, LOCKED, NOT_ISSUED), `delivery_overrides_total`. Worker: `sms_messages_total` (template: a registry key, outcome: sent, failed, skipped), `job_duration_seconds`/`job_failures_total` (queue, name), `queue_jobs` (queue, state), `outbox_unpublished_events`, `outbox_oldest_unpublished_age_seconds`, `payment_reconciliation_mismatches_total`, `stock_reconciliation_mismatches_total` (kind: ON_HAND, RESERVED_MOVEMENTS, ACTIVE_RESERVATIONS, LOT_MOVEMENTS, LOT_TOTAL, SERIAL_UNITS). Both: `velocity_limit_hits_total` (rule, level), `velocity_check_errors_total` (stage: screen, record). API: `cod_gate_refusals_total` (gate). Record through `AppMetrics` (global `ObservabilityModule`); labels must stay bounded (no ids, raw paths or variable values). Alert rules: `ops/prometheus/alerts.yml` (drills in `alerts.test.yml`; see `docs/roadmap/environments.md` → Observability). A port clash fails startup; the API and worker need different ports when they share a network namespace.
- **Velocity checks (P3-E.1, `src/fraud/`):** fixed-window counters in Redis (one Lua script increments every counter of an event and sets its TTL = window) per customer, phone (E.164), IP and card (Paystack authorization signature, from verified attempts, failed-payment counts only). Keys are `velocity:<rule>:<sha256(subject type + value)>`: never a raw phone, IP or card in Redis, the database or logs. The rule catalogue and default limits are code (`src/fraud/velocity-rules.ts`, pure); the Owner overrides limits (`VelocityLimit`, `payment.settings.manage`, step-up, audited). `createOrder` and `POST /payment/initialize` are screened before they run: above a hard limit `FORBIDDEN` + `reason: VELOCITY_LIMIT`; above a soft limit the order gets an `OrderReviewFlag` (staff list them with `order.view`, clear them with `order.manage`, audited). Settlement only flags (customer and card failures). Events are counted after the action succeeds, so concurrent requests can overshoot a limit by a few. Redis failure: fail-open with an error log and `velocity_check_errors_total`.
- **Disputes (P3-E.2, `src/payment/disputes/`):** `Dispute` per captured attempt (provider dispute id unique per provider) with append-only `DisputeNote` (staff evidence) and `DisputeEvent` (status history), both refusing updates and direct deletes by trigger. Status moves only through the pure table in `dispute-status.ts` (OPEN, AWAITING_EVIDENCE, UNDER_REVIEW → WON, LOST, ACCEPTED). Paystack `charge.dispute.*` webhooks are validated and mapped to a provider-neutral `DisputeNotice` in `paystack-dispute.ts`; the inbox stores only that notice (keyed per dispute id + `updatedAt`) and the webhook job applies it idempotently under a row lock. Staff record disputes, add notes and change status with `payment.dispute.manage` (Owner, Manager), audited; reads need `payment.view`. Opening one records `payment.dispute_opened.v1` (the worker logs ids only). `RefundsService.send` calls `DisputesService.assertRefundAllowed` first: an unresolved dispute → `CONFLICT` + `reason: PAYMENT_DISPUTED`; a LOST/ACCEPTED dispute counts as charged back against the refundable amount.
- **Prisma enums/models** also cover fulfillment (`FulfillmentType`, pickup locations, shipping zones), taxes, promotions (`Promotion`, `CouponCode`, `Redemption`), price lists (`PriceList`, `PriceListEntry`, `PriceListTier`), return requests and the stock ledger (`StockLocation`, `StockLevel`, `StockReservation`, `StockMovement`, `Lot`, `LotStock`).

### Testing

Unit tests are colocated as `*.spec.ts` under `src/`. E2E tests live in `test/e2e/` (`*.e2e-spec.ts`) with shared helpers in `test/helpers/` and `test/setup.ts`; they use a separate database and Redis configured in `.env.test` (not committed — create it from `.env.test.example` or with `node scripts/write-test-env.js <DATABASE_URL> [redis://host:port/db]`; `test/setup.ts` refuses to run unless the database name ends in `_test`).
