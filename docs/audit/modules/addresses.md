# Addresses
Verdict: NEEDS WORK (authorization is correct; the data model does not fit Ghana and delete/edit semantics are unsafe)
Reviewed by: Customer-Features reviewer, Claude Sonnet 5.5, default effort
Files reviewed: `src/addresses/**` (resolver, service, repository, dto/, entity, module, 3 specs), `prisma/schema.prisma` (Address, Order), `src/order/order.service.ts` (address use at checkout), `src/shipping-zones/shipping-zones.service.ts`, `src/commons/filters/all-exceptions.filter.ts`, `test/e2e/address.e2e.spec.ts` (names).

## Summary
Object-level authorization is correct: every user-facing read/update/delete goes through `retrieveUserAddress`, which compares `address.userId` with the caller and returns NotFound for someone else's id (no existence oracle). The weaknesses are the model and its edges: US-style fields (`zipCode` required, no phone, recipient, landmark, GhanaPostGPS digital address, region), city is free text yet drives the shipping fee, deleting an address that was used by an order fails with "Internal server error", and admin address queries are role-gated but unaudited and the super-admin variant returns every address in the system unpaginated. The resolver spec suite fails to compile.

Why `addresses.resolver.spec` fails (baseline question): the resolver's `getAllAddresses` gained a required first parameter `@ActiveUser('role') role` (`addresses.resolver.ts:44-47`), but the spec still calls `resolver.getAllAddresses()` with no arguments (`addresses.resolver.spec.ts:89,143`), so ts-jest reports TS2554 and no test in the suite runs. A stale test, not a runtime bug. Confirmed by running the spec.

## Positives (checked, no defect)
- `getAddress`, `updateAddress`, `deleteAddress` all enforce `address.userId === caller` before acting; the repository update/delete then act on the id only after that check (no TOCTOU of consequence because `userId` is not editable: it is omitted from `UpdateAddressInput`).
- `createAddress` takes `userId` from the token, not from input.
- Checkout validates the address belongs to the user (`ensureValidShippingAddress`) before use.

## Test assessment
Service/repository specs pass (mock-based); resolver spec fails to compile. No behaviour-level tests for the Ghana fields (they do not exist yet), delete-with-orders, or admin PII access.

## Definition of done to close this module
1. Ghana-ready model and validation (ADR-01, ADR-04) with a migration and region/zone alignment.
2. Safe delete/edit for addresses referenced by orders (ADR-02, ADR-03).
3. Admin reads paginated and audited (ADR-05).
4. Fix the resolver spec and add cross-user authorization tests (ADR-10).
