# Inventory
Verdict: NEEDS WORK (ledger and restock are sound; the stock model around them is not)
Reviewed by: Order, Inventory & Payment reviewer, Claude Opus 5.5, high
Files reviewed: `src/inventory/**` (service, repository, resolver, module, dto, entities, enums, specs), `src/inventory/tasks/low-stock.task.ts`, every writer of `Product.quantity` / `Variant.quantity` in `src/` (`order.service.ts`, `order.repository.ts`, `returns.repository.ts`, `products.service.ts`, `variant.service.ts`, `cart.service.ts`), `prisma/schema.prisma` (Product, Variant, InventoryLog, StockStatus), `prisma/migrations/*` (no CHECK constraints).

## Summary
The admin restock path is correct: an atomic increment inside a transaction, a log row in the same transaction, and `quantityAfter` taken from the locked UPDATE's result. That makes it accurate under concurrency. The order-deduction path is equally sound (see `order.md`). The problems sit in the stock model around the module. Product and variant stock are two independent numbers, and only product stock is ever consumed. Several writers bypass the ledger entirely: admin product/variant update (absolute overwrite), soft-delete restore and refund restore. Restoration paths aren't exactly-once. There's no adjustment/decrement operation, no `quantity >= 0` constraint, and `stockStatus` is never maintained. The `InventoryLog` therefore can't be reconciled with `Product.quantity`, and the low-stock "alerts" are log lines nobody receives.

### What is correct (keep)
- Restock: atomic `increment` + log in one transaction, `quantityAfter` from the updated row (`inventory.service.ts:28-42`, `59-74`). Under concurrency each `UPDATE` holds the row lock, so `quantityAfter` is exact.
- Order deduction logs `ORDER_DEDUCTION` in the same transaction (`order.service.ts:363-376`).
- All inventory resolvers are `ADMIN`/`SUPER_ADMIN` at class level (`inventory.resolver.ts:9`). The restock input is validated (`@IsInt @Min(1)`).

## Test assessment
`inventory.service.spec.ts` and `inventory.repository.spec.ts` pass but are mock-call assertions (Prisma mocked). They don't exercise concurrency, the ledger-vs-balance invariant, or the bypass writers. No test checks that every quantity change produces a log row. The low-stock task has no spec.

## Definition of done to close this module
1. One stock source of truth (variant-level), consumed by cart/order/return.
2. All stock writes go through inventory operations (deduct, restore, restock, adjust) that are conditional, logged in the same tx, and idempotent per reference. `quantity` removed from product/variant update inputs.
3. DB CHECK `quantity >= 0`. Availability derived or maintained transactionally.
4. Paginated log queries. Log rows carry a reference. History survives product deletion.
5. Invariant test: for each product, `initial + Σ(log.quantityChange) = quantity` after a scripted order/cancel/refund/restock run, plus concurrency e2e.
