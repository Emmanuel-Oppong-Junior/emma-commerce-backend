# Payment
Verdict: REWRITE (verification/webhook/state handling); the Paystack integration skeleton can be kept
Reviewed by: Order, Inventory & Payment reviewer, Claude Opus 5.5, high
Files reviewed: `src/payment/**` (service, repository, resolver, controller, module, constant, dto, entities, enums, all specs), `src/types/paystack-api.d.ts`, `prisma/schema.prisma` (Payment, Order, PaymentStatus), git history of `src/payment/payment.repository.ts` and `payment.service.ts` (commits `2470013`, `f46f0d7`), `test/e2e/payment-return.e2e-spec.ts`, `TODO.md` payment items, `node_modules/@nestjs/graphql/dist/{services/gql-execution-context.js,utils/normalize-resolver-args.js}` (REST guard behaviour). The security agent owns HMAC verification. It's noted here only where it affects business behaviour.

## Summary
The design is sound in one respect: neither the webhook nor the redirect trusts the event payload. Both re-fetch the transaction from Paystack by reference. Everything around that is broken. The order update after verification is unconditional. It used to be guarded with `status: PENDING`, the guard was removed in commit `2470013`, and the still-failing repository test documents the original intent. As a result, a replayed verify or a duplicate or late webhook moves SHIPPED, DELIVERED and CANCELLED orders back to PROCESSING. Payment initiation doesn't check order status, lets the client pick the currency, deletes the in-flight PENDING payment (orphaning a reference the customer may still pay), and after a FAILED attempt can never succeed again because of `Payment.orderId @unique`. Amount and currency returned by Paystack are never compared with the order. The webhook returns 200 even when processing failed, and there's no reconciliation job, so a missed webhook is a lost payment. Refund and reversal states don't exist.

### What is correct (keep)
- Both webhook and redirect re-verify with Paystack's API by reference instead of trusting the payload (`payment.service.ts:68-73`).
- Ownership enforced on `verifyPayment` (403) and on initiation (`payment.service.ts:82-90`, `241-246`).
- Sanitised `paymentDetails` (no PII/authorization objects stored) (`payment.service.ts:312-333`).
- COD orders blocked from online initiation (`payment.service.ts:47-49`).

## Test assessment
Unit: service spec mostly mocks the repository and asserts calls. One test is red because behaviour changed. The repository spec's red test is correct and exposes PAY-01. No tests cover duplicate webhooks, late success on a cancelled order, amount/currency mismatch, FAILED → retry, or re-initiation while a checkout is live. E2E: initialize and verify are tested with `PaymentService` fully mocked (they only prove routing and auth). The webhook success path is untested. Scratch repros for PAY-01/02/04/05 pass (they demonstrate the defects).

## Definition of done to close this module
1. `PaymentAttempt` (N per order, unique reference, never deleted) plus a `Refund` table. Status enum covers PENDING/COMPLETED/FAILED/ABANDONED/REVERSED/REFUNDED/PARTIALLY_REFUNDED.
2. Verification is idempotent and side-effect-once. Amount, currency and reference must match the attempt. Order transition goes through the order state machine. Success on a non-PENDING order triggers a defined compensation (re-reserve or auto-refund + alert).
3. Initiation only for PENDING, non-deleted ONLINE orders. Server-chosen currency. Reuse the live attempt. Concurrency-safe (unique constraint + conditional insert).
4. Webhook: raw-body HMAC with constant-time compare. Event inbox with dedupe. 5xx on failure. Refund/dispute events handled.
5. Reconciliation cron (single-runner, see CRON) for PENDING attempts.
6. COD collection only from SHIPPED, transactional, audited. Payments not deletable.
7. Tests for every path in `docs/audit/_work/order-lifecycle.md` §2, including webhook e2e with a real signature. Suites green.
