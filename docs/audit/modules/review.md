## Summary
Ownership rules for update/delete are correct and score is validated 1-5. But a review's `user` field resolves to the full `User` type, and `User.addresses`/`User.orders` have no authorization, so any visitor who can read a product's reviews (the `products`/`product` queries are public) can read every reviewer's email, phone number, home addresses and order history (REV-01, confirmed with a harness). There is no verified-purchase requirement, no database uniqueness for one review per user per product (app check only, racy), unbounded comment text, no moderation workflow, soft-delete columns that nothing uses, no rating aggregate, and unbounded review lists. `review.service.spec.ts` does not compile, so its 14 tests do not run.

## Positives (checked, no defect)
- Score is `@IsInt @Min(1) @Max(5)`.
- `updateReview`/`deleteReview` verify `review.userId === caller` before changing anything, so user A cannot modify or delete user B's review.
- User deletion cascades their reviews; product deletion cascades its reviews.

## Test assessment
Repository spec passes; service spec does not compile (14 tests dormant); resolver spec is a stub. The only authorization and duplicate checks are in the e2e file, which is not runnable in this environment.

## Definition of done to close this module
1. `Review.user` replaced by a minimal public author type; regression test for anonymous and authenticated callers (REV-01).
2. Verified-purchase rule and DB uniqueness (REV-02/03).
3. Comment length/sanitisation and creation rate limit (REV-04).
4. Moderation status, soft-hide, audited admin actions, loader filtered by status (REV-05).
5. Pagination and a maintained rating aggregate (REV-06).
6. Repair `review.service.spec.ts` and add integration tests for races and exposure (REV-09).
