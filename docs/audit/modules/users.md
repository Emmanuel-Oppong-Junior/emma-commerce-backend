# Users
Verdict: NEEDS WORK (one Critical data-exposure defect, USR-01, must be fixed before any public launch)
Reviewed by: Customer-Features reviewer, Claude Sonnet 5.5, default effort
Files reviewed: `src/users/**` (resolver, service, repository, dto/, entities/, loaders/, module, 3 specs), `src/iam/authentication/guards/{roles,access-token,authentication}.guard.ts`, `src/iam/authentication/authentication.service.ts` (callers only), `src/app.module.ts` (GraphQL config), `src/main.ts` (ValidationPipe), `src/commons/filters/all-exceptions.filter.ts`, `src/commons/error-formatters/grapqhl-error.formatter.ts`, `prisma/schema.prisma` (User, AuthProvider, Order FK), `schema.gql`, `test/e2e/` (names only).

## Summary
Profile and admin CRUD are small and mostly sound: `UpdateUserInput` has no `role`/`isActive`, global `ValidationPipe` uses `whitelist + forbidNonWhitelisted`, so mass-assignment of role is not possible; `SUPER_ADMIN` is protected from update/delete/archive and hidden from the list; `isActive` is checked on every request and on refresh, so archiving takes effect immediately. The serious problems are (1) the `addresses` and `orders` field resolvers on `User` have no authorization and are reachable from any `User`-typed field (e.g. `Review.user`), which exposes every reviewer's email, phone, home addresses and order history to anonymous callers (USR-01); (2) email can be changed without verification or re-authentication and admins can rewrite peer admins' emails (USR-02/03); (3) hard delete and unique-constraint errors surface as "Internal server error" (USR-05/06). Spec health: users resolver and 2 service tests fail (stale fixtures).

Why `users.resolver.spec` and `users.service.spec` fail (baseline question): they are stale tests, not code bugs. `users.resolver.spec.ts:103` builds a `pageInfo` without `totalCount` (now required by `PageInfo`), so the suite fails to compile; `users.service.spec.ts:141,165` expect `findMany` to be called with a `where` that lacks `role: { not: SUPER_ADMIN }`, which `buildWhereClause` (`users.service.ts:129-139`) now always adds. Confirmed by running both specs.

## Positives (checked, no defect)
- `updateMyProfile` cannot change role or `isActive` (not in input; `forbidNonWhitelisted` rejects extras).
- `adminUpdateUser`/`archive`/`remove`/`deArchive` reject `SUPER_ADMIN` targets; `createUser` rejects `SUPER_ADMIN` role and is `SUPER_ADMIN`-only.
- Deactivated users are cut off immediately (access guard re-reads the user per request; refresh checks `isActive`).
- Password hash, reset token and lockout fields are not in the GraphQL type.

## Test assessment
Colocated specs: repository (passes), service (2 of 18 fail, stale), resolver (suite fails to compile). Coverage is mock-only and does not exercise role guards, field-level exposure or DB constraints. E2E `user-account.e2e-spec.ts` exists but could not run (no `.env.test`; helper broken per baseline), so none of the authorization claims above are covered by a real test.

## Definition of done to close this module
1. Fix USR-01 (no unauthorised `addresses`/`orders` on `User`; public reviewer projection) and add a GraphQL-level regression test that a plain user and an anonymous caller cannot read another user's addresses/orders/email/phone via reviews, orders and orders.
2. Email change requires verification and re-auth and revokes sessions; add `emailVerifiedAt` (USR-02).
3. Admin actions cannot target peer `ADMIN`s unless caller is `SUPER_ADMIN`; all user mutations audited (USR-03).
4. Replace hard delete with anonymisation; map Prisma P2002/P2003 centrally (USR-04/05/14).
5. Phone normalisation to +233 and non-empty validation; stop lowercasing names (USR-05/06).
6. Repair the two failing specs and add the missing guard-level tests (USR-13).
