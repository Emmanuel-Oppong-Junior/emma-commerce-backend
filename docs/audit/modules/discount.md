# Discount

## Summary
Discounts are displayed (product `discountedPrice`, `cartWithDiscount`) but never applied to the amount charged: `createOrder` prices every line at `Product.price` and does not call the discount service (see MONEY-01 in `_work/money-flow.md`). The only path that writes discounts onto an order, the user-callable `finalizeOrder` mutation, overwrites `Order.totalAmount` with the gross subtotal at current prices, dropping shipping and coupon, so a customer can remove the shipping fee from an unpaid order before paying. The "best discount" picker compares a percentage number against a cedi amount, discount amounts are not capped at the price, and all arithmetic is unrounded float. The data model allows a category or variant to belong to only one discount. Fixing this needs a single server-side pricing function used by catalogue, cart and checkout, not patches to the current three copies.

## Definition of done to close this module
1. One pricing function (pure, Decimal/pesewas, documented rounding) that takes sellable unit, quantity, active campaigns, coupon and returns line and order breakdowns; used by catalogue loader, cart and `createOrder`.
2. `createOrder` applies it inside the transaction and persists immutable snapshots (`unitPrice`, `discountAmount`, `discountId` + name/type/value, `lineTotal`) on `OrderItem` and `subtotal`, `discountTotal`, `couponDiscount`, `shippingFee`, `taxTotal`, `totalAmount` on `Order`.
3. `finalizeOrder` removed; reads (`cartWithDiscount`) have no writes.
4. Selection compares actual cedi value; amount capped at unit price; minimumPurchase is an eligibility filter; stacking/priority rules written down and enforced.
5. Discount ↔ category/variant are many-to-many join tables; DB CHECK constraints on value; soft delete + audit log.
6. Specs compile and cover: mixed-type selection, caps, % > 100 on update, minimumPurchase, rounding examples (19.99 × 3 @ 15%), time window edges, and an e2e that the amount sent to Paystack equals the discounted total.
