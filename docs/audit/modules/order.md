# Order
Verdict: REWRITE (of the status/stock-restoration core; creation path is salvageable)
Reviewed by: Order, Inventory & Payment reviewer, Claude Opus 5.5, high
Files reviewed: `src/order/**` (service, repository, resolver, module, dto, entities, enums, specs), `src/order/tasks/expired-orders.task.ts`, checkout parts of `src/cart/**`, `src/discount/discount.service.ts:205-209,356-374` and `src/discount/discount.repository.ts:121-162` (reached from `finalizeOrder`), `src/coupons/coupons.repository.ts:61-64`, `src/shipping-zones/shipping-zones.service.ts:57-60`, `prisma/schema.prisma` (Order, OrderItem, Product, Variant, CartItem, Payment), `test/e2e/order.e2e-spec.ts`, `FRONTEND_API_DOCUMENTATION.md` §2.11 and order-flow section. Lifecycle diagram: `docs/audit/_work/order-lifecycle.md`.

## Summary
Order creation is the one part done right: stock is decremented with an atomic `UPDATE … quantity - n` inside an interactive transaction, a negative result rolls the whole order back, and the inventory log, coupon usage and cart clear are in the same transaction. Everything after creation is unsafe. There is no state machine. Stock restoration is neither conditional nor idempotent, so any customer can re-cancel a cancelled order and add stock without limit. Admin delete restores stock from any status. Status writes inside "transactions" go through the root Prisma client rather than `tx`. Variants are ignored end to end. A customer-callable `finalizeOrder` rewrites the order total and drops the shipping fee. Abandoned orders that reached payment keep their stock forever. The unit suites for the service and resolver fail at dependency injection, so none of this is tested. The restoration and transition logic needs a redesign: a transition table, conditional `updateMany … WHERE status IN (…)` and restore-only-on-a-winning-transition. Patching individual call sites won't fix it.

### What is correct (keep)
- Atomic, conditional-by-rollback stock decrement in one interactive transaction, with an `ORDER_DEDUCTION` log whose `quantityAfter` comes from the row returned by the locked UPDATE (`order.service.ts:362-376`). Two buyers racing for the last unit: the second UPDATE waits on the row lock, sees −1 and rolls back.
- Ownership on `order`, `cancelOrder` and `finalizeOrder` via `retrieveUserOrder` (`order.service.ts:393-399`) returns 404 for other users' orders. Admin-only resolvers are role-gated.
- Shipping-address ownership check (`order.repository.ts:123-125`) and the address snapshot on the order.

## Test assessment
Unit: zero effective coverage. Both suites die in `beforeEach` (baseline). The repository spec passes but only asserts Prisma call shapes. E2E (not runnable: no `.env.test`; `test/helpers/db.helper.ts` fails typecheck) covers create/cancel/finalize happy paths and a "cancel DELIVERED fails" case. It doesn't cover re-cancel, concurrency, expiry, delete, COD, PICKUP, or variant orders. The `finalizeOrder` e2e asserts the endpoint "works", which locks in the ORD-05 behaviour. Scratch repros for ORD-01/03/04 were written outside the repo (see final message) and pass, which means they demonstrate the defects.

## Definition of done to close this module
1. One `OrderLifecycleService.transition(orderId, to, actor, tx)` enforcing an explicit transition table, using conditional `updateMany` (or `FOR UPDATE`) as the claim. Stock restoration, coupon release, history row and audit happen only when the claim succeeds, inside the same transaction. Emails go out after commit.
2. ORD-01..07 fixed, each with a failing-first test. DB-backed e2e for: last-unit race, double cancel, cancel vs expiry race, delete doesn't move stock, late payment on an expired order.
3. Variant-aware cart → order → stock (ORD-06). Product checks (active/published/expiry/price) inside the tx.
4. `finalizeOrder` removed or made internal. Totals (subtotal, discounts, coupon, shipping, tax) snapshotted once at creation.
5. Reservation expiry independent of the Payment row, COD confirmation/expiry, and a per-user open-order cap.
6. Checkout idempotency key. Paginated order lists. Status history with timestamps.
7. Unit suites green. Docs regenerated from the implemented state machine.
