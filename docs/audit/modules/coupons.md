## Summary
The basics are right: the coupon is resolved server-side by code at `createOrder`, the discount is computed on the server subtotal (the client's `orderTotal` is only used by the preview mutation), FLAT is capped at the subtotal, and one-use-per-user is enforced by the `@@unique([couponId, userId])` index inside the order transaction, so two parallel orders from the same user can't both use it. Defects: the global `usageLimit` check runs outside the transaction and the increment is unconditional, so concurrent checkouts by different users overspend a limited coupon. Usage is never released when an order is cancelled or expires unpaid. PERCENTAGE value is unbounded. The validate endpoint is a code/state oracle behind only the global rate limit. There is no defined stacking rule with product discounts.

| CPN-01 | High | Concurrency | `usedCount >= usageLimit` is checked in `validateCoupon` before the order transaction starts; inside the transaction `recordUsage` inserts `CouponUsage` and does an unconditional `usedCount: { increment: 1 }`. The per-user unique index does not help because the users differ. Probe: two validations against `usageLimit 1, usedCount 0` for users u1/u2 both pass. | `coupons.service.ts:93-95`; `coupons.repository.ts:61-64`; `order.service.ts:306-310, 384-386` | Confirmed by reading; pre-check race confirmed by test (probe) | "First 100 customers" promotions overspent during launch bursts; direct margin loss proportional to concurrency. | Inside the order transaction do a conditional increment and check the row count, e.g. `tx.coupon.updateMany({ where: { id, isActive: true, OR: [{ usageLimit: null }, { usedCount: { lt: tx.coupon.fields.usageLimit } }] }, data: { usedCount: { increment: 1 } } })` and throw if `count === 0` (or raw `UPDATE … WHERE "usedCount" < "usageLimit" RETURNING`). ## Definition of done to close this module
1. Conditional, atomic usage increment inside the order transaction with row-count check; validity re-checked there; DB CHECK on `usedCount`.
2. Usage released in the same transaction as cancel/expiry (and a written policy for refunds).
3. PERCENTAGE bounded (DTO, service on merged entity, DB CHECK); optional max-discount cap; amounts rounded half-up to 2 dp with Decimal.
4. Written stacking rule with product discounts, implemented in the shared pricing function.
5. Dedicated throttle and a single generic error for `validateCoupon`; preview computed from the server cart.
6. Tests: concurrency (limit 1, two users), PERCENTAGE > 100 rejected, rounding cases (20.10 @ 25%), release on cancel; e2e updated to the current `CreateOrderInput`.
