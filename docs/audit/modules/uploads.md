# Uploads (REST image upload → sharp → Cloudinary)
Verdict: NEEDS WORK
Reviewed by: IAM & Security reviewer, Claude Opus 5.5, high
Files reviewed: `src/commons/upload.controller.ts`, `src/commons/interceptors/file-upload.interceptor.ts`, `src/commons/cloudinary.service.ts`, `MulterModule` config in `src/app.module.ts:109-111`, `src/commons/commons.module.ts`, global guards/interceptors that wrap the controller.

## Summary
The live path (`POST /upload/single-image`, `POST /upload/multiple-images`) uses in-memory Multer with a 5 MB / 3-file limit, re-encodes through sharp (500×500) and uploads to Cloudinary. Today the endpoints cannot succeed at all: the global GraphQL logging interceptor (PLAT-01) and the GraphQL-only access-token guard (IAM-07) both throw on HTTP requests. Once that is fixed, any logged-in customer could upload, there is no content-type validation, and a failed sharp decode silently uploads the raw bytes. A second, unused upload helper writes to local disk trusting client mimetype and extension.

## Test assessment
No unit or e2e tests exist for `UploadController` or `CloudinaryService` (`grep upload test/` returns nothing). The cloudinary health indicator has its own spec (owned by health.md).

## Definition of done to close this module
1. UPL-01 fixed and covered by an e2e test (admin token, small PNG, Cloudinary mocked → 201 with `url`/`public_id`).
2. Admin-only role check; tests for USER → 403 and anonymous → 401.
3. Magic-byte allowlist, reject on sharp failure, forced output format, pixel limit; tests with an SVG, a text file renamed `.png`, and an oversized-dimension PNG.
4. Asset ownership persisted and an admin delete path.
5. Dead `FileUploadInterceptor` and `MulterModule` `dest` removed.
