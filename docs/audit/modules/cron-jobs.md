## Summary
Both jobs are in-process `@nestjs/schedule` crons with no leader election or lock. They run on every replica, and in every e2e test app that imports `AppModule`. The low-stock job is read-only, so duplicates only produce noise. The expiry job is not safe to run twice: its status update is unconditional and the order snapshot is stale, so every extra instance restores stock again. Its selection criteria are also wrong. Orders with an abandoned or failed payment are never expired, which locks stock, while orders mid-payment can be expired. The low-stock "alert" is only a log line that nobody is notified about. The jobs the payment flow actually needs (payment reconciliation, refund status) don't exist.

## Test assessment
No tests for either task. `expireAbandonedOrders` sits in the dead `order.service.spec.ts` suite (DI failure) and isn't tested even there.

## Definition of done to close this module
1. Every job is single-runner (advisory lock or external scheduler/queue) **and** individually idempotent (conditional claims), so a double run is harmless either way.
2. Expiry driven by a reservation deadline, rechecked in the tx, Paystack-aware, batched, error-isolated, configurable, releasing coupon usage and notifying the customer.
3. Payment reconciliation and refund-status jobs added.
4. Low-stock produces a deduplicated admin digest.
5. Unit tests for job services. Scheduling disabled in test env.
