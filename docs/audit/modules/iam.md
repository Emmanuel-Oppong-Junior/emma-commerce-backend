# IAM (authentication, tokens, roles, social login, auth paths in users)
Verdict: NEEDS WORK
Reviewed by: IAM & Security reviewer, Claude Opus 5.5, high
Files reviewed: `src/iam/**` (resolver, service, guards, decorators, DTOs, social services, jwt.config, bcrypt), `src/users/users.service.ts`, `users.repository.ts`, `users.resolver.ts`, `users/dto/*`, `users/entities/user.entity.ts`, `prisma/schema.prisma` (User, RefreshToken, AuthProvider), `test/e2e/auth.e2e-spec.ts`, IAM unit specs, `node_modules/@nestjs/{jwt,throttler,graphql,core}` sources where behaviour mattered.

## Summary
The skeleton is reasonable: separate secrets for access/refresh/reset tokens, `aud`/`iss` checked, refresh tokens and reset tokens stored as SHA-256 hashes, bcrypt cost 12, user re-loaded from the DB on every request (so deactivation and role changes take effect immediately), global `AuthenticationGuard` + `RolesGuard` wired as `APP_GUARD` in the right order. But the token lifecycle is weak: a stolen refresh token survives password reset and can be extended forever, rotation is not race-safe and has no reuse detection, tokens are deterministic (no `jti`). Social login links a provider identity to any existing account with the same email, which together with unverified sign-up allows account pre-hijacking (including admin accounts if a provider ever returns an unverified email). The sign-in DTO rejects passwords longer than 16 characters although sign-up accepts 64, so some customers can register but never log in. All Bearer-protected REST routes crash because the guards only understand GraphQL context.

## Test assessment
- `npx jest src/iam src/commons` → 9 suites / 29 tests pass. All are mock-based: they assert that mocks were called (e.g. "should atomically rotate" only checks `rotateRefreshToken` was called), so none would catch IAM-02/03/04/08. Guard specs are "should be defined" only; `authentication.guard.spec.ts` has an empty test.
- No tests for social account linking, lockout concurrency, HTTP-context guards, token-type confusion, or password-length parity between DTOs.
- e2e `auth.e2e-spec.ts` has the refresh happy path and the whole `signOut` block commented out; e2e is not runnable (no `.env.test`, `test/helpers/db.helper.ts` fails typecheck per baseline).

## Definition of done to close this module
1. IAM-01: verified-email-only auto-linking (Google `email_verified`, Facebook explicit link flow), sign-up email verification, no auto-link to admin roles; e2e test for the pre-hijack scenario.
2. IAM-02/03/04: `jti` on all tokens, conditional rotation in a transaction, family revocation on reuse, absolute session cap, revoke all refresh tokens on password reset/change/deactivation/email change; unit tests against a real DB for concurrent refresh.
3. IAM-05/06: one password policy shared by all DTOs; test that any password accepted at sign-up is accepted at sign-in.
4. IAM-07: context-type-aware guards and `@ActiveUser`; e2e for `/payment/initialize` and `/upload/single-image` with a valid token returning 2xx.
5. IAM-08/09/10: atomic lockout counter with generic message; re-auth + verification for email change; SUPER_ADMIN-only control over admins; audit log for user-admin actions.
6. IAM-11/12: encoded provider calls with timeouts and id cross-check; `typ` claim checked; Joi enforces distinct secrets.
7. Restore the commented e2e tests and make the e2e suite runnable in CI.
