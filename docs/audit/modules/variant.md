## Summary
Variants are an admin-side CRUD over `Variant{size?, color?, quantity, price}` that nothing in cart, order, or stock logic consumes: `AddToCartInput` has no `variantId`, and cart/order services never reference variants, so a customer can only buy the parent product at the parent's price and stock. The model is hard-coded to size/color (no SKU, no option matrix), allows duplicates and attribute-less variants, sets stock without inventory logs, and any logged-in customer can list every variant in the system. For a multi-vertical platform (fashion, electronics storage/RAM, pharmacy strengths/pack sizes, furniture finishes, beauty shades) this needs a redesign, not patching.

## Test assessment
`variant.{service,repository,resolver}.spec.ts` pass but verify that mocks were called. There are no tests for validation boundaries, FK behaviour, concurrency, or integration with cart/order (because none exists). The e2e suite is broad on role matrix but encodes VAR-03 as expected behaviour and cannot be run in the current environment.

## Definition of done to close this module
1. Decide and document the variant/stock model (variants own stock and price when present; product-level stock otherwise); remove or derive `Product.quantity` for variant products.
2. Replace `size`/`color` with option definitions and option values; unique option combination per product; per-variant SKU/barcode/image; `isActive`.
3. Cart, order, returns and inventory use `variantId` end to end (stock check, price, atomic decrement, log, restore).
4. Variant stock only changes through the audited inventory path; initial stock logged.
5. Customer-facing variant data only via published products; admin-only `variants` query, paginated.
6. DTO validation (int quantity, bounded decimal price, existence checks) and FK errors mapped to Conflict/NotFound.
7. Behavioural unit and e2e tests (runnable `.env.test`) covering the above.
